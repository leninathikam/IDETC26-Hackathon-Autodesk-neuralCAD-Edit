Yes. Given your current architecture, I would **not add another general-purpose LLM/critic layer**. Your biggest opportunity is to make the deterministic geometry path much more surgical and make the LLM retries receive **structured geometric evidence about exactly what failed**.

The key observation is:

> Your 0.07–0.10 Diff F1 suggests the system is often solving the *semantic instruction* but failing at **binding the instruction to the exact geometric entities and extent of the edit**.

For the hard chamfer example, the gap between GPT's 0.679 and your ~0.30 is especially strong evidence of that.

# 1. Make edge/hole binding a first-class optimization problem

This is probably your **highest ROI change**.

Right now, "find circular edges matching fitting diameter" is good, but diameter alone is not enough.

For a part containing:

* Ø1.26 mm holes
* Ø2 mm holes
* multiple holes of the same diameter
* countersinks
* cylindrical bosses
* unrelated circular edges

you need to rank **candidate geometric entities**, not simply filter them.

For every candidate circular edge/hole, construct something like:

```text
candidate:
    edge_id
    radius
    center
    axis
    adjacent_face_types
    adjacent_face_count
    hole_depth
    through_hole
    local_bbox
    distance_to_part_bbox
    distance_to_other_holes
    concentric_with_other_edges
```

Then score it against the instruction.

For:

> Add 0.2 mm chamfer to the hole edges

the selection should be approximately:

```text
hole candidate
    ↓
diameter matches fitting_hole_diameter
    ↓
is actually part of cylindrical hole
    ↓
edge belongs to hole rim
    ↓
not an unrelated circular outer edge
    ↓
select intended rim(s)
```

### Even better: distinguish "hole" from "circular edge"

This distinction is huge.

Instead of:

```python
find_circular_edges(diameter)
```

have:

```python
find_hole_rims(
    diameter=...,
    location_hint=...,
    through=True/None,
)
```

Internally, identify a hole through its **cylindrical face + axis + rim topology**, then derive its boundary edges.

That prevents a circular outer boundary from being mistaken for a hole rim.

### For multiple same-diameter holes

Don't immediately apply the operation to every match.

Generate:

```text
candidate set A = all matching rims
candidate set B = spatially clustered matching rims
candidate set C = matching rims associated with the same hole family
```

Then use the instruction's location hint and topology to choose.

This directly targets your:

> wrong edge/hole binding

failure mode.

# 2. Add a chamfer/fillet feasibility policy before applying the requested dimension

Your recent radius cap is a good fix, but I would make it **feature-aware rather than a single global cap**.

For a circular hole rim:

```text
requested distance = 0.2 mm
hole radius = 0.63 mm

0.2 / 0.63 = 0.317
```

That is already fairly aggressive.

Instead of:

```python
distance = min(requested, 0.28 * radius)
```

I'd use a policy like:

```text
requested d
      ↓
local radius
      ↓
neighboring-face thickness
      ↓
adjacent edge distances
      ↓
maximum geometrically plausible d
      ↓
try requested d
      ↓
if OCC fails:
    binary-search feasible d
```

The important distinction is:

### Don't silently replace the requested dimension with a smaller one.

If the requested 0.2 mm works:

```text
use 0.2
```

If it fails:

```text
0.2 → 0.15 → 0.10 → 0.05
```

Then record:

```json
{
  "requested": 0.2,
  "applied": 0.1,
  "feasible": true,
  "degraded_dimension": true
}
```

That gives your retry layer valuable information.

### Better still: OCC feasibility search

For local blends, you can make the tool itself:

```text
select candidate edges
↓
try requested dimension
↓
OCC success?
    yes → accept candidate
    no → reduce dimension
```

rather than sending the failed geometry to the LLM.

That should eliminate a class of:

> OCC blend fails → LLM unnecessarily reconstructs/retries

failures.

# 3. Make `INCOMPLETE_PLAN` an explicit classifier outcome

I strongly recommend adding this.

Currently you have something like:

```text
edit_type
target_kind
dims
high_confidence_local
cadquery_strategy
```

Add:

```text
plan_status:
    COMPLETE
    INCOMPLETE
    AMBIGUOUS
```

And explicitly track:

```text
required:
    operation
    target
    dimension
    location
    extent
```

For example:

### "Add a 0.2 mm chamfer to the hole edges"

Potentially:

```json
{
  "operation": "chamfer",
  "target": "hole_rim",
  "dimension": 0.2,
  "location": null,
  "extent": "all_matching_holes",
  "confidence": 0.94,
  "plan_status": "COMPLETE"
}
```

But:

> "Chamfer the hole near the side"

might become:

```json
{
  "operation": "chamfer",
  "target": "hole_rim",
  "dimension": null,
  "location": "side",
  "extent": "single",
  "plan_status": "INCOMPLETE"
}
```

Don't let the system hallucinate the missing dimension.

Instead:

```text
INCOMPLETE
    ↓
infer only if geometry/instruction makes it deterministic
    ↓
otherwise controlled LLM strategy
```

This is especially important because **invented dimensions can destroy Diff F1 while still producing a visually plausible part**.

# 4. Make retry feedback geometric, not prose-heavy

This is another big opportunity.

I would stop giving the next CadQuery iteration generic messages like:

> The previous attempt failed because the geometry was oversized.

Instead produce a compact **delta report**.

For example:

```text
EDIT DELTA REPORT

Requested:
  chamfer 0.2 mm
  target: hole rims
  expected scope: 4 rims

Previous result:
  chamfered rims detected: 7
  expected candidate rims: 4
  added faces: +14
  removed faces: +0
  volume change: -0.021 mm³
  bbox change: 0.00 mm

Failure:
  OVER_SELECTION

Target candidates:
  [E17, E21, E43, E48]

Incorrect candidates:
  [E51, E52, E61]

REWRITE REQUIREMENT:
  Start from original STEP.
  Select only rims belonging to the 4 identified hole cylinders.
  Do not chamfer unrelated circular edges.
  Preserve all other geometry.
```

That's dramatically more useful to the LLM than:

> Try again and make the chamfer more localized.

### Give the LLM explicit "do not repeat" information

For each retry:

```text
Attempt 1:
  selected 7 rims
  expected 4

Attempt 2:
  selected 2 rims
  expected 4

Attempt 3:
  ...
```

The LLM then gets a trajectory instead of repeatedly rediscovering the same solution.

# 5. Add a topology fingerprint specifically for the requested edit

Your current dual critic is already doing useful work.

I'd add a lightweight **edit signature**.

For example, a chamfer should typically produce:

```text
cylindrical hole
    ↓
additional conical/frustum-like transition
    ↓
original cylindrical wall
```

So after the operation, inspect:

```text
face count delta
surface-type delta
edge count delta
cylindrical-face count
conical-face count
local volume delta
local bbox delta
```

Then classify:

```text
EXPECTED_CHAMFER
NO_EFFECT
OVER_EDIT
WRONG_FEATURE
```

For example:

```text
requested chamfer
expected:
    +1 conical face / rim
    local volume decrease
    same global bbox

actual:
    +0 conical faces
    volume unchanged

=> NO_EFFECT
```

That is much stronger than relying on generic volume/bbox similarity.

### Especially important for identity

Your current:

```text
IDENTITY_OUTPUT
```

should be expanded from global geometry into **local geometry**.

An identity edit can be detected with:

```text
global difference ≈ 0
AND
target-region difference ≈ 0
```

But the inverse is equally important:

```text
global difference small
AND
target-region difference matches expected
```

should be a strong positive signal.

# 6. Create an "expected locality envelope"

This could become one of your best protections against over-editing.

Every edit gets an expected spatial envelope.

Example:

```text
target:
    hole center = (x,y,z)
    radius = 0.63

locality envelope:
    center ± 2r
```

Then measure:

```text
changed geometry inside envelope
changed geometry outside envelope
```

For a hole chamfer:

```text
inside target envelope: 98% changed
outside envelope: 2% changed
```

Good.

Whereas:

```text
inside: 70%
outside: 65%
```

is almost certainly wrong.

This gives you a powerful additional critic:

```text
LOCALITY_OK
LOCALITY_VIOLATION
```

without violating your geometry-only acceptance rule.

# 7. For boolean/add/delete edits, use local construction rather than reconstruction

This is where I would modify your:

```text
mutate
reconstruct
```

strategy.

Don't treat all reconstruction operations equally.

I'd split them into:

```text
LOCAL_BOOLEAN
LOCAL_ADDITION
LOCAL_DELETION
PATTERNED_LOCAL_EDIT
GLOBAL_STRUCTURAL_EDIT
```

### Example: hole addition

Prefer:

```text
import STEP
↓
identify support face
↓
construct cylinder at target location
↓
boolean cut
↓
validate
```

not:

```text
reconstruct body with new hole
```

### Example: boss addition

Prefer:

```text
import STEP
↓
identify support face
↓
construct local cylinder
↓
union
↓
validate
```

Again, preserve the imported body as the base.

### Example: slot deletion

Prefer:

```text
identify local slot geometry
↓
construct removal volume
↓
boolean operation
```

rather than rebuilding the entire solid.

The principle should be:

> **Reconstruct the edit volume, not the part.**

That's probably the most important architectural rule for your boolean/addition branch.

# 8. Add candidate generation before LLM CadQuery

Instead of immediately asking the LLM:

> Write CadQuery to chamfer the correct hole.

Have the geometry layer generate candidates:

```text
Candidate 1:
  hole #3
  Ø1.26
  center (...)
  rim edges [17,18]

Candidate 2:
  hole #5
  Ø1.26
  center (...)
  rim edges [31,32]

Candidate 3:
  outer circular edge
  Ø1.26
  NOT hole
```

Then the LLM receives:

```text
TARGET CANDIDATES

C1: valid hole, Ø1.26, location A
C2: valid hole, Ø1.26, location B
C3: circular edge, NOT hole

Instruction: ...
```

This is much easier for the LLM to reason over than raw geometry.

And importantly, you're still obeying:

> no raw STEP/B-Rep dumps.

You're giving it a **geometry census / typed representation**, exactly as your constraints require.

# 9. Use "edit intent → expected geometric delta" before execution

This is a subtle but high-value change.

Your classifier currently determines:

```text
what operation should happen
```

Add:

```text
what should change geometrically
```

For example:

### Chamfer

```json
{
  "expected_delta": {
    "volume": "decrease_small",
    "bbox": "unchanged",
    "faces": "increase",
    "locality": "target_rim"
  }
}
```

### Hole

```json
{
  "expected_delta": {
    "volume": "decrease",
    "bbox": "unchanged",
    "cylindrical_faces": "+1",
    "locality": "target_face"
  }
}
```

### Boss addition

```json
{
  "expected_delta": {
    "volume": "increase",
    "bbox": "possibly_increase",
    "faces": "increase",
    "locality": "target_face"
  }
}
```

Now your verifier isn't just asking:

> "Did geometry change?"

It's asking:

> **"Did geometry change in the way this particular edit should change it?"**

That's much closer to what Diff F1 actually rewards.

# 10. Optimize the evaluation around edit localization

I would add several diagnostics alongside your official Diff F1.

Not as replacement metrics, but as **debugging metrics**.

### A. Edit-region precision

```text
predicted changed voxels
∩
GT changed voxels
--------------------------------
predicted changed voxels
```

### B. Edit-region recall

```text
predicted changed voxels
∩
GT changed voxels
--------------------------------
GT changed voxels
```

Then:

```text
Diff F1 = harmonic mean
```

But also record:

```text
pred_delta_volume / gt_delta_volume
```

This immediately distinguishes:

```text
under-edit
correct edit
over-edit
```

For example:

```text
GT delta volume:       1.0
prediction delta:      7.8
intersection:          0.9
```

means:

> You found the correct region but edited far too much.

That's a very different problem from:

```text
GT delta: 1.0
pred delta: 0.9
intersection: 0.05
```

which means:

> Wrong location.

Those should trigger **different retries**.

# The retry policy I'd implement

This is probably the cleanest immediate change to your pipeline.

```text
                 Execute
                    │
                    ▼
              Geometry critic
                    │
          ┌─────────┴─────────┐
          │                   │
       ACCEPT               FAIL
                              │
                              ▼
                     classify failure
                              │
        ┌─────────────┬───────┼──────────────┐
        ▼             ▼       ▼              ▼
     NO-OP        OVEREDIT  WRONG TARGET   OCC FAIL
        │             │       │              │
        ▼             ▼       ▼              ▼
   strengthen      narrow    rebind        reduce
   operation       scope     candidate      dimension
        │             │       │              │
        └─────────────┴───────┴──────────────┘
                              │
                              ▼
                       next CadQuery
```

This is better than simply:

```text
FAIL → "try again"
```

because each failure category requires a different intervention.

# One architectural change I'd prioritize above everything else

I'd make `patterns.py` return not merely a `ToolCall`, but an **EditPlan**.

Something like:

```text
EditPlan
├── operation
├── target_kind
├── target_candidates
├── selected_candidates
├── dimensions
├── location
├── expected_scope
├── expected_delta
├── locality_envelope
├── confidence
├── plan_status
└── fallback_strategy
```

Then:

```text
classifier
      ↓
   EditPlan
      ↓
 deterministic tool
      ↓
 geometry result
      ↓
 expected_delta comparison
      ↓
 accept / failure classification
      ↓
 targeted retry
```

That creates a clean separation between:

**what should change**
and
**how CadQuery happens to implement it**.

Right now, I suspect some of your failures happen because those two concepts are getting mixed together.

## My top 5 implementation order

If you want the **best Diff F1 improvement per engineering hour**, I'd do these in this order:

### 1. 🥇 Hole/edge candidate binding

Build robust `hole → cylindrical face → rim edge` relationships and rank candidates.

**Why:** directly attacks wrong-region Diff F1 failures.

### 2. 🥈 Feature-specific blend feasibility

Requested dimension → OCC attempt → bounded fallback/binary search.

**Why:** eliminates avoidable failed chamfers/fillets and unnecessary LLM retries.

### 3. 🥉 `EditPlan + expected_delta`

Make every edit carry expected topology, volume, bbox, and locality changes.

**Why:** turns your critic from "is this different?" into "is this the *right kind* of difference?"

### 4. Targeted retry feedback

Generate structured `NO_OP / OVER_EDIT / WRONG_TARGET / OCC_FAIL` feedback.

**Why:** makes each LLM iteration corrective rather than stochastic.

### 5. Local boolean/addition/deletion operators

Preserve the imported STEP and construct only the local edit volume.

**Why:** should substantially improve the harder 28, where reconstruction is likely introducing unrelated differences.

## One thing I would *not* optimize yet

I wouldn't spend much time improving the visual iteration loop from 3 → 5 → 8 iterations.

Your current numbers don't scream **"the LLM needs more attempts."**

They scream:

> **"The system needs to know exactly which geometry is supposed to change."**

If GPT gets **0.679 Diff F1** on the hard chamfer while your deterministic/LLM system gets ~0.30 at best, I would focus on **entity binding + edit extent + geometric delta verification** before increasing model sophistication.

The winning architecture here is probably not "smarter CAD generation." It's **smarter geometric grounding around a relatively ordinary CadQuery generator**. That fits your existing harness extremely well and, importantly, directly optimizes the metric Autodesk actually cares about: **the voxels that changed, not whether the final object merely looks like the same part.**
